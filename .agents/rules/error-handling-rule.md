# قاعدة عامة إلزامية — معالجة الأخطاء والاستثناءات

**النطاق:** جميع مشاريع Flutter/Dart، وبالأخص مشروع رونقك. تطبق هذه القاعدة عند إنشاء أو تعديل أو مراجعة أي `try/catch` أو `.catchError()` أو Future أو معالجة أخطاء Riverpod/Dio أو التخزين أو المصادقة.

## القاعدة الأساسية

ممنوع منعاً باتاً إنشاء أو إبقاء `catch` فارغة أو شكلية لا تنفذ معالجة مفيدة، مثل:

```dart
catch (_) {}
catch (e) {}
catch (_) { return; }
catch (_) { return null; }
catch (_) { return const []; }
```

ويُمنع أيضاً التقاط الخطأ ثم إرجاع قيمة افتراضية تجعل العملية الفاشلة تبدو ناجحة، أو إخفاء الخطأ لمجرد منع ظهور مشكلة للمستخدم.

**كل `catch` يجب أن تحقق واحداً أو أكثر من الآتي بصورة صحيحة ومبررة:**
1. تحويل الخطأ المعروف إلى حالة فشل واضحة ومناسبة في التطبيق.
2. إظهار أو حفظ رسالة مفهومة وآمنة للمستخدم، مع إتاحة إعادة المحاولة عند الحاجة.
3. تسجيل الخطأ تشخيصياً أو إرساله إلى Sentry إذا كان غير متوقع ويستحق المتابعة، مع StackTrace والسياق الآمن.
4. تنفيذ fallback حقيقي ومسموح لا يزوّر نجاح العملية ولا يمسح بيانات صحيحة، مع توضيح أن البيانات قديمة/محلية عند الحاجة.
5. إعادة رمي الخطأ الأصلي باستخدام `rethrow` إذا كانت هذه الطبقة لا تملك صلاحية معالجته.

التسجيل وحده ليس معالجة كافية إذا بقيت حالة التطبيق خاطئة أو غير محددة.

## شرط الاستقرار

لا تعالج المشكلة بإزالة `catch` عشوائياً ولا بإعادة رمي كل الأخطاء إلى أعلى التطبيق. المطلوب معالجة صحيحة تمنع الانهيار غير الضروري وتحافظ على استقرار الواجهة، مع إظهار الفشل بصدق. لا يجوز اعتبار فشل الشبكة أو التخزين أو الدفع نجاحاً، ولا يجوز إرجاع بيانات وهمية أو فارغة على أنها بيانات حقيقية.

## ضوابط إلزامية

- لا تستخدم `try/catch` حول كود لا يحتاج معالجة.
- لا تستخدم `catch (e) { throw e; }`؛ استخدم `rethrow` عند الحاجة للحفاظ على StackTrace.
- لا تحول `ApiException` أو `ValidationException` أو `UnauthorizedException` إلى خطأ عام مثل `NetworkException(500)`.
- لا تستخدم `unawaited()` للعمليات الحرجة مثل حفظ/مسح التوكن أو الدفع أو إنشاء الطلب. أي Future غير منتظر يجب أن يمتلك معالجة أخطاء صريحة ومبررة.
- استخدم `finally` للتنظيف وإعادة ضبط `isLoading` وتحرير الموارد، بدلاً من catch فارغة.
- لا تمسح Cache صحيحاً عند فشل تحديث الشبكة.
- لا تعرض `e.toString()` الخام للمستخدم، ولا تسجل Tokens أو كلمات مرور أو بيانات دفع أو بيانات شخصية حساسة.
- لا ترسل أخطاء التحقق المتوقعة أو الإلغاء الطبيعي إلى Sentry كحوادث غير معالجة إلا إذا كانت سياسة المشروع تنص على ذلك. تجنب تسجيل الخطأ نفسه من عدة طبقات.
- لا تضف حزمًا ولا تغيّر معمارية المشروع أو Riverpod/Dio دون موافقة صريحة.

## سير العمل

1. ابدأ بتدقيق Read-only للكتل الحالية وسياقها ومواضع استدعائها.
2. صنّف كل حالة: معالجة صحيحة، fallback مبرر، إعادة رمي زائدة، ابتلاع صامت، أو خطأ Future غير مراقب.
3. اقترح خطة إصلاح مرحلية واختبارات قبل التعديل.
4. نفّذ فقط المرحلة المعتمدة.
5. اختبر مسار النجاح والفشل والتعافي، ثم شغّل `flutter analyze` والاختبارات المرتبطة.
6. في التقرير النهائي أكد صراحةً عدم إضافة أي `catch` فارغة أو شكلية، واذكر نتائج الأوامر الفعلية دون ادعاء.

**المبدأ الحاكم: لا نريد تطبيقاً ينهار بسبب كل خطأ، ولا تطبيقاً يخفي أخطاءه ويتظاهر بأن كل شيء يعمل. نريد معالجة فعلية، حالة صحيحة، تشخيصاً قابلاً للصيانة، وتجربة مستخدم مستقرة.**
