# Mandatory Engineering Rules — Non-Negotiable

هذه القواعد إلزامية في جميع عمليات التحليل والتطوير والإصلاح والتحسين، ولا يجوز تجاوزها إلا بموافقة صريحة من المستخدم.

## Rule 1: Architecture Change Authorization

**ممنوع تغيير معمارية المشروع دون موافقة صريحة من المستخدم.**

- لا تستبدل نظام إدارة الحالة الحالي.
- لا تنقل المشروع إلى Clean Architecture أو أي معمارية أخرى تلقائيًا.
- لا تعِد هيكلة المجلدات والطبقات دون ضرورة وموافقة.
- لا تستبدل GetX بـ Riverpod أو BLoC أو العكس.
- لا تنفذ Migration واسعة أثناء إصلاح مشكلة محدودة.
- حافظ على الأنماط والاتفاقيات المعتمدة في المشروع.

إذا كان تغيير المعمارية ضروريًا، اشرح المشكلة والفوائد والمخاطر والبدائل، ثم انتظر موافقة المستخدم قبل التنفيذ.

## Rule 2: Evidence-Based Performance Optimization

**ممنوع الادعاء بتحسين الأداء دون أدلة أو قياسات فعلية.**

- لا تدّعِ تقليل استهلاك الذاكرة دون قياس أو دليل تقني.
- لا تدّعِ تحسين سرعة التطبيق دون مقارنة موثوقة.
- لا تصف الكود بأنه أسرع لمجرد أنه أقصر أو أكثر تعقيدًا.
- لا تدّعِ تقليل عدد طلبات API دون التحقق من الطلبات الفعلية.
- استخدم Flutter DevTools وPerformance View وMemory Profiler عند الحاجة.
- قارن النتائج قبل التحسين وبعده في ظروف متقاربة.

إذا تعذر إجراء القياسات، استخدم وصفًا دقيقًا مثل: "تحسين محتمل" أو "تقليل عمليات غير ضرورية بناءً على تحليل الكود"، ولا تدّعِ تحقيق تحسن مثبت.

## Rule 3: Verification Beyond Flutter Analyze

**نجاح `flutter analyze` وحده لا يُعتبر دليلًا على سلامة التطبيق أو اكتمال الإصلاح.**

يجب التحقق من الجوانب المناسبة لطبيعة التغيير، بما يشمل:

- Static Analysis.
- Unit Tests.
- Widget Tests.
- Integration Tests عند الحاجة.
- Build Verification عند الحاجة.
- Regression Testing.
- التحقق من السلوك الفعلي عند الحاجة.

يجب التمييز بوضوح بين:

1. فحوصات تم تنفيذها ونجحت.
2. فحوصات تم تنفيذها وفشلت.
3. فحوصات لم يتم تنفيذها.
4. سلوك تم التحقق منه يدويًا.
5. أمور لم يتم التحقق منها بعد.

ممنوع الادعاء بأن التطبيق سليم أو أن المشكلة حُلّت بالكامل اعتمادًا على التحليل الثابت فقط.

## Enforcement

- هذه القواعد أعلى أولوية من أي اقتراح تحسين تلقائي.
- لا يجوز تجاوزها لأسباب تتعلق بالسرعة أو سهولة التنفيذ.
- عند تعارض مهمة المستخدم مع إحدى هذه القواعد، وضّح التعارض وانتظر التوجيه إذا كان التنفيذ يتطلب تجاوزها.
- يجب تطبيقها على جميع الملفات والميزات والمراحل، وليس فقط الملفات التي يتم تعديلها مباشرة.

**Any violation of these rules is considered an engineering process failure.**
